# Contract reality - contract versus actual (tracked continuously)

A living ledger that continuously tracks the gap between "what the contract says in the docs" and "what actually runs that way". When a gap is found it goes into this table first; when it is filled the row is deleted. Development principle 4 (from the ground up: measure, then contract, then implement) points at this table.

Why this document lives in the persistent docs rather than in a plan: a mainPlan initiative moves to `_done` when it completes, so it cannot be the canonical home for a standing policy. This table is an engineering-honesty device consulted every time the engine version moves or a capability changes, so it lives here.

## Open debt (what needs filling now)

| Item | Contract | Actual | Next action |
|---|---|---|---|
| Implicit FFI/fetch assumptions | Survives an engine swap or update | Direct `toJs` is isolated to PyodideEngine alone, and the host contract is `proxyMode`/`fallback`. EngineContract validates version, kind, and capabilities at construction, and WASI and Pyodide share a minimum RuntimeContract | A new engine must pass both `tests/contracts/runtimeContract.mjs` and browser measurement |
| A single source for Web Computer runtime assets | Runtime assets come from a reproducible path | The opaque `buildroot-bzimage68.bin` is still a development fallback. Alongside it there is now an own recipe that emits the exact Buildroot source and config, legal-info, CycloneDX, and a build manifest | Confirm byte identity across two independent builds plus the Web Computer gate, then switch the catalog to `buildroot-pyproc-i686.bin` |
| Reactive and %undo memory | Safe even in long sessions | A resident base is a foundational premise. `history.stats()` and the retention budget observe base, delta, hash, and node pressure, and off-path branches can be auto-pruned. There is still no automatic rebase of the live path | Collect pressure events from real long-lived workloads and judge a safe-rebase design as its own initiative |
| Verification evidence for shipped surfaces | Every shipped public surface has an automated gate | `pyproc/gpu` and `pyproc/socket` have zero headless CI gates (GPU has no adapter; socket depends on a relay this package does not ship). Verification falls to manual probes and the consuming product | Where a gate is impossible, state the strongest available comparison instead (for GPU, shader byte identity is the ceiling). Until then both subpaths are marked "shipped, no headless gate" in the README and held under the Experimental freeze |
| Cross-engine byte path between guests | The host generalizes across engines, so any two guests on one switch can exchange bytes | Python-to-Python frame exchange is proven in CI (`guestNetworkProbe`, 9 checks), and the Linux side has a port, but nothing puts a Python guest and the x86 Linux guest on the same switch. The Linux crossing probe still pairs Linux against a JS fixture peer | One probe where Linux pings the Python guest's address and a Python-sent frame arrives inside Linux, surviving a commit and a cold restore. That is what turns co-residency into the general claim |
| Handles that enter the heap without `setGlobal` | The image-portability refusal sees every JS handle in the heap | The count sits on the engine's `globals.set`, which is where the shipped wrapper mints one, and a structure gate now fixes the set of places that may call it (the engine itself, plus the worker kernel that has no `Runtime` wrapper and writes no image). Two paths remain outside any count and cannot be brought inside: guest Python can `import js` itself, and `rt.raw` hands out the engine by design for `deviceFs`-class consumers. So the refusal is a floor for shipped surfaces, not a proof about arbitrary guest code | State that boundary wherever the guarantee is quoted. Closing it entirely needs engine-level accounting of handle allocation, which is upstream work |
| A portable image and a blocking surface | `snapshotScope: "portable"` means a machine image revives and keeps working | A JS handle is interpreter-local and cannot cross an image: measured across thirteen bisected cases, a kernel revived from an image whose seed installed one traps on every proxy path, including handles the revived kernel mints itself. The packet port and the permission jail were moved to value boundaries (pure Python plus bytes and literals through `run()`), so they cross intact. What cannot move is a **blocking** surface - the syscall bridge behind `input()`, sockets, GPU - because blocking Python on a JS answer needs a handle by construction. `exportImage` and `save` now refuse such a heap with `PYPROC_IMAGE_PROXY_SURFACE` and name the surfaces, and `{ allowHostProxies: true }` is the explicit acknowledgement: the revived kernel keeps its plain Python state and loses those surfaces | Either an engine-level way to rebind handles after materialisation, or a blocking mechanism that needs no handle. Until one exists the refusal is the contract, and the browser gate holds both directions (refused by default, and the acknowledged path still works) |
| The wire is turn-based | A guest can build TCP, UDP, or DNS on the frame contract | `src/machine/` creates no worker, so both guests and the host share one JS thread. The switch's microtask pump cannot run while Python is on the stack, so `pyprocNet.recv()` only ever sees frames that arrived *between* `run()` calls. No handshake can wait for a reply inside one turn | Host guests in workers (an adapter-side proxy over a MessagePort plus port-bridged devices). Until then the frame contract is real but the invitation to build a stack on it is not reachable |

## Documented tradeoffs (intended contracts)

| Item | Tradeoff | Stated condition |
|---|---|---|
| `PYTHONHASHSEED=0` always pinned | The deterministic boot path (internal `bootSession`) hardcodes it, and CPython reads it once at interpreter initialization, so **hash randomization is off for the whole session** (defeating the hash-flooding mitigation from CVE-2012-1150). V8 solves the same problem by fixing the seed at build time and rehashing with a fresh seed at deserialization, but CPython has no rehash facility, so determinism and seed freshness cannot both be had | Under the threat model the damage is confined to your own session in your own tab, and only for workloads that bulk-load external input as dict keys. Replay determinism is the core of this library, so the tradeoff is taken and stated |
| Three global stubs | The entropy/time swap (session boot) and the fetch swap (the wheelCache install window) are restored in a `finally`, but they are visible to concurrent work inside that window | Concurrent boots are forbidden: `runExclusive` in the internal `bootSession` serializes session boots. Stated in the consumer docs |
| ReactiveController.saveBase | Only backs up or moves the base; RAM does not shrink, because the restore path assumes a resident base. The memory valves are pruneTo and dispose | Comments and types corrected to say backup/move (2026-07-16). A real offload (per-page file restore) conflicts with the synchronous restore contract and is not started |
| The WASI session value bridge | JSON-serializable only (no FFI). Functions, numpy arrays, and live objects cannot cross | A separate async surface (bootWasi). Pyodide is the production canon (the runtime-consistency section of [contract.md](../consuming/contract.md)) |
| machineJail parent isolation | The CSP connect-src blocks the jail's own network egress, but a same-origin jail leaves a `window.parent` side channel open | Full isolation means an opaque origin (sandbox), and the price is losing crossOriginIsolated, hence SharedArrayBuffer, hence fork and interrupt - so a jailed machine is a single Runtime |
| One memcpy for shared memory | A SAB cannot be exposed into the Python heap with zero copies (the single-linear-memory wall) | `PyProc.shm` and `mapArray` keep "one memcpy" as a public contract |
| The Immortal Python Machine recovery boundary | It does not revive an arbitrary moment's execution stack and in-flight external requests; a new leader continues execution from the heap plus `/home/web` of the last completed commit | An RPC whose leader vanished after it was sent ends as `PYPROC_RPC_OUTCOME_UNKNOWN` with `retryable=false` and is never replayed automatically. A product must not resend the same command without an explicit idempotency policy |

## Frontier (the honest wall is WASM dlopen)

- Warm fork (cloning after package load with zero re-imports), true shared-memory threads (nogil), and zero-copy numpy between processes are all blocked on one unsolved problem: WASM dlopen plus cross-instance and cross-thread memory sharing. That is an upstream research problem, not "a few weeks of building".
- pyproc (independent interpreter workers plus message passing) avoids exactly that problem. Each worker owns its own wasmTable, heap, and glue, so there is no dlopen mismatch. That is why this is the highest reachable point today, and why the frontier is a wall rather than a stepping stone.
- The map of four states per capability (achieved today / workaround available / waiting on upstream / permanent wall) is canonical in "The four states of a capability" in [docs/product/vision.md](../product/vision.md).
