# Capability matrix

This table exists so a product can decide which pyproc capabilities it may rely on. It is not an implementation map or an install guide: it groups the public surface by product value, current status, prerequisites, runnable surface, verification, and boundaries.

Canonical sources are split:

- Install, version pinning, import boundaries: [contract.md](contract.md)
- The speed-measurement contract: [benchmarking.md](../operations/benchmarking.md) (measurements live only in ledgers and artifacts. Speed is something you measure yourself with the Speed Lab, not a number posted here for you to trust)
- `.pymachine` trust and the permission UI: [trustPermissions.md](trustPermissions.md)
- Portable bundle (`PYBUNDLE1`) envelope layout: [bundleFormat.md](../reference/bundleFormat.md)
- Reopening product resources after a revival: [resumeCatalog.md](resumeCatalog.md)
- Environment compatibility (browser, JSPI, COOP/COEP, engine, resource characteristics) on one page: [compatibility.md](compatibility.md)

Status labels match the README's Feature status. Stable means a surface you can put on the default product path. Beta means you can ship it, but with the browser conditions and a fallback alongside. Experimental means it needs an explicit product mode and observation. Research preview means it is a surface that proves an engine possibility.

## Promotion criteria (labels move on criteria, not on impressions)

| Label | Promotion conditions (all required) |
|---|---|
| Stable | (a) A CI runtime gate covers the real behavior. (b) At least one release has passed since the last breaking change (evidence the surface is frozen). (c) A 30-day soak with the gate continuously green. (d) The boundaries - what it does *not* do - are documented here and in the reference. |
| Beta | (a) and (d). Browser conditions and fallback requirements are stated in the table. |
| Experimental | A runnable surface and a verification command exist (a manual probe is acceptable). |
| Research preview | Its identity as a proof vehicle is stated, along with what the production canon is instead. |

Demotion is immediate: if a gate disappears or a breaking change lands, the label drops with no conditions attached.

### Promotion ledger

Rows that carry the Stable label are recorded here with their evidence. A Stable row absent from this ledger is blocked by the structure gate: a label rising without a documented basis is drift.

| Surface | Stable since | Basis |
|---|---|---|
| Python runtime (`boot`/`run`/`loadPackages`) | before 2026-07-15 | (a) browser gate always on, (b) surface frozen across many 0.0.x releases, (c) long soak with the gate continuously green, (d) documented |
| Deployment asset integrity | before 2026-07-15 | (a) browser plus install-tarball gates, (b) releases elapsed, (c) long soak with the gate continuously green, (d) documented |

Promotion waiting clock: reactive (checkpoint/restore), session (.pymachine), and machineJournal were
re-judged at v0.0.11. Their persistence, portability, and failure contracts changed in that release,
so v0.0.11 is the new reference point for release stability. Calling a lane Stable in the same
release that changes its boundary would erase the meaning of the label.

A runnable surface is an example a person opens, a browser gate, a probe, or a tracked benchmark artifact. Every product claim must be reproducible through one of the runnable surfaces in the table below.

## Product decision rules

- The README's Public surface is an API list. This document is the table that groups those APIs into product decision units backed by runnable evidence.
- Even for a row at Beta or above, do not turn the feature on unless `checkEnvironment()` and your deployment preflight pass.
- Keep Experimental rows behind an explicit product mode rather than in the default feature set.
- Where the browser physically blocks something - inbound sockets and arbitrary native binaries above all - pyproc alone promises nothing. Those need a relay, an agent, a static build, or a change in the platform.
