# 소비 저장소 피드백 계약

pyproc을 사용하는 제품에서 브라우저 조작이나 시각 검수를 수행하다가 pyproc 자체의 결함, 빠진 능력,
불명확한 공개 계약을 발견했을 때 적용하는 접수 계약이다. 목표는 소비 저장소의 우회 코드를 늘리는 것이
아니라, 한 번의 실측을 다른 제품도 재사용할 수 있는 pyproc 이니셔티브로 바꾸는 것이다.

## 1. 접수 판정

다음 조건을 모두 만족할 때만 pyproc 피드백으로 접수한다.

1. 소비 저장소가 고정한 정확한 pyproc 설치본과 공개 `pyproc-control` 명령 또는 공개 패키지 표면에서
   관찰했다.
2. 합성하거나 비식별화한 입력으로 다시 재현할 수 있다.
3. 원인이 호출 제품의 도메인 규칙, UI 구현, 잘못된 설정만으로 설명되지 않는다.
4. 해결했을 때 둘 이상의 소비 시나리오 또는 pyproc의 명시된 계약이 좋아진다.

추측, 기능 아이디어 한 줄, 소비 저장소에만 해당하는 요구는 `mainPlan/`에 넣지 않는다. 계약과 실제가
이미 어긋난 경우에는 [계약 실태 표](./contract-reality.md)에도 현재 차이를 기록한다.

## 2. 접수 순서

1. pyproc의 `CLAUDE.md`, `mainPlan/README.md`, 이 문서, `contractReality.md`를 읽는다.
2. `mainPlan/`, `skills/`, `tests/attempts/`, Git 이력에서 같은 원인과 계약을 검색한다.
3. 같은 이니셔티브가 있으면 새 계획을 만들지 않고 그 `README.md`에 별도 관찰 사례를 보탠다.
4. 새 이니셔티브라면 현재 직렬 대기열의 끝에
   `mainPlan/<다음번호>-<camelCase능력이름>/README.md`를 만들고 `mainPlan/README.md`의 순서에
   연결한다. 기록은 가능하지만 현재 선행 이니셔티브를 건너뛰어 구현하지 않는다.
5. 소비 작업 중 발견했다는 이유만으로 pyproc 소스를 함께 고치지 않는다. 사용자가 upstream 개선까지
   맡긴 경우에만 정해진 순서에서 `tests/attempts/` 실측을 시작한다.

소비 작업을 안전하게 마칠 수 있으면 마치되, 영구 우회를 제품 계약으로 굳히지 않는다. 안전하게 계속할
수 없으면 현재 작업의 차단 지점과 pyproc 피드백 경로를 소비 저장소에도 남긴다.

## 4. 증거와 개인정보 경계

pyproc 저장소에는 실제 자격증명, 쿠키, 세션 토큰, 수집 기록, 고객 자료, 사용자 파일, 로컬 브라우저
profile, 민감한 스크린샷을 넣지 않는다. 절대 로컬 경로 대신 논리 이름을 쓰고, 로그는 비밀을 제거하며,
페이지와 데이터는 최소 합성 fixture로 다시 만든다. 원본 증거가 소비 장치 밖으로 나갈 수 없다면
`mainPlan`에는 비식별 요약, digest, 재현 절차만 남긴다.

## 5. 종료

피드백은 보관함이 아니라 미완료 제품 이니셔티브다. 재현 probe, 계약, 구현, 수용 테스트, 브라우저
실측, 지속 문서 반영이 끝나면 해당 `mainPlan/` 폴더와 대응 `tests/attempts/` 폴더를 같은 사이클에
삭제한다. 완료 근거는 정식 테스트와 Git 이력이 보존한다.
